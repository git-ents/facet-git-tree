# Independent Evaluation: Append-Only Git-Model Database (amended design)

Reviewer register: CIDR. Judged independently on soundness, novelty, shipability; amendments A–C are evaluated as part of the design.

---

## 1. Taxonomy translation

A **log-structured, copy-on-write Merkle trie store with persistent-roots concurrency and tracing-GC retention**.

- **Storage engine:** an LSM without memtables or levels — the commit graph _is_ the log; "compaction" is `git gc`/pack, i.e. mark-sweep + delta recompression, not key-range merge.
- **MVCC:** each ref head is a root commit; reading a ref is a snapshot. Reads are snapshot-isolated per object graph but **read committed across refs** — two refs read in one "transaction" see unrelated points in time; no multi-ref read snapshot.
- **Writes:** optimistic concurrency on a single record (the ref value). Not serializable. Writers CAS ref advancement in a linear order, but their state changes were computed against possibly-divergent bases and reconciled by **three-way merge** — convergence with application-defined conflict surfacing. A lost-update window exists unless the CAS payload pins the expected base. The precise name: **optimistic multi-version merge, per-ref, non-transactional across refs**. Merge is not a concurrency control; it is a reconciliation protocol.
- **Session guarantees:** monotonic reads _if_ the client pins a snapshot OID; monotonic writes only per-ref. No read-your-writes guarantee exists across the async write-back window. Causal consistency is achievable only if ref advance piggybacks the predecessor OID — unstated.
- **Register semantics:** each ref is a CAS-resolved multi-valued register — last-writer-wins per ref; the register value is a merged tree, not a CRDT: contents merge, register values don't.
- **Tracing GC:** rooted reachability from live refs plus pins, minus tombstone negation (amendment C). A tracing collector whose _root set spans two trust domains_ — that is the hard part.

**Consistency contract:** per-ref linear order of pointer advances (CAS); snapshot reads at any past ref; no cross-ref atomicity; no serializable transactions; conflicts via deterministic three-way merge or explicit refusal. This is Git's model — honest, but "readers are lock-free snapshots" hides that _writers_ are lock-free optimists too.

## 3. Assumption stress

**A1 (COW write amplification).** Path rewrite cost per update ≈ tree depth × node size. With Git's per-directory fanout (~10³ entries/tree at ~4 KB), a 10⁷-key corpus has depth ≈ 3 at fanout 256 (measured: 256-entry tree node ≈ 9.2 KB) ⇒ ~28 KB dirty per key update (estimate). Crossover with in-place B-tree + WAL sits at **>5–10 path rewrites per flush window per key** (estimate) — the design fails when a _narrow hot set_ (10³ keys) absorbs 10⁴ updates/sec: each flush rebuilds the same path, giving ~300 KB dirty per 1 KB logical change (WA ≈ 300×). Batching one new root per flush restores WA ≈ depth, which beats leveled-LSM. **Settling evidence:** WA curve vs. hot-set cardinality against RocksDB leveled (WA ~10–20) on 10⁷ keys. Falsifier: any hot-set size where sustained throughput < 0.1× RocksDB's.

**A2 (CAS throughput).** A ref is a single CAS point ⇒ per-ref advance is fully serialized; receive-pack does ~10¹–10² ref updates/sec (measured locally: 55–73 ms/op via CLI, incl. process spawn — upper bound; in-process fsync-bound CAS is below that). Comfortable at agent scale; a hard ceiling at 10⁴ writers. The escape is frontier sharding — what ref-per-partition accidentally provides. The design should _claim_ ref-partitioning as concurrency sharding, not just retention. **Evidence:** ref-advance latency under 10²–10⁴ writers in a deterministic simulator.

**A3 (optimistic unique constraints).** Verify-and-CAS degrades with retry probability p (expected attempts = 1/(1−p)); p ≈ 0.5 doubles latency, p → 1 livelocks. Near-p-free on high-entropy keys (content OIDs); livelocks on low-entropy keys (usernames, sequential IDs) exactly when it matters. **Evidence:** Jepsen-style contended-insert test. Falsifier: throughput collapse or constraint violation at 50% conflict.

**A4 (Expired contract).** Empirically confirmed (stock repo, deleted blob): `git diff` aborts `fatal: unable to read <oid>` (exit 128), `git fsck` reports `missing blob` (corruption), and `git cat-file` says `Not a valid object name` — none distinguishing pruned from corrupt from never-existed. The promisor path adds no distinction: expired objects surface through generic transport failures; stock `git-upload-pack` sends no distinguishable error code. The contract survives only for first-party readers. **Remaining:** libgit2 CI and a graph walker against an expired remote. Falsifier: any mainstream consumer unable to distinguish Expired from corruption.

**A5 (pins as reachability extension).** A pin on a mid-tree OID keeps a _disconnected sub-DAG_ live: a tree-pin retains an unprunable island whose edges to pruned parents force dangling-tree walks forever, breaking pack dedup assumptions. Retention-coupling pathology: an attestation pin on a 7-day build CAS object forces a 90-day partition to retain referential meaning. The pin registry, being non-content mutable metadata, needs its own consistency/durability story — unsupplied.

## 4. Missing invariants

The four-invariant set is **not complete**. Silently assumed:

1. **Encoding determinism.** Content identity presupposes canonical encoding. Verified in `src/ser.rs::float_text`: the codec canonicalizes NaN and negative zero — but otherwise delegates floats to Rust's `Display`, i.e. shortest-round-trip decimal with Rust tie-breaking and no exponent notation. Deterministic within Rust, not across implementations: a JS writer emits `1e+21` where Rust emits `1000000000000000000000`, splitting one fact into two identities. The frozen identity normal form (raw IEEE-754 bits) sidesteps this for keys; the general codec still violates the premise the edifice sits on. This is an invariant, not an implementation note.
2. **Non-content metadata consistency.** Amendment C concedes tombstone-propagation state, the pin registry, and the ref store are mutable non-content — a small _mutable database inside the immutable database_ with no stated durability/ordering/replication contract. The "one tiny mutable frontier" claim recurses and was never closed.
3. **Durability of the async write-back window.** Local fsync + ref advance, remote async: a crash in the window loses facts the local user believed recorded. Either the record is truth (local must not report success before durable remote write) or it is eventually consistent ("WORM record" overstated). The prose claims both.
4. **Naming and authority.** Who may CAS a ref? Ref names are the entire security and partitioning model; an authority model (signing, capability, push rules) is load-bearing for the "record" claim and is absent.
5. **Cross-partition reachability edges.** Facts referencing objects across retention partitions (agent log → build CAS) make scopes non-orthogonal; "ref-per-partition" silently assumes edges are intra-partition.

## 5. The proposer's open questions

**(a) Invariants complete?** No — missing determinism, metadata-layer mutability, and authority (§4.1–4.4).

**(b) Where does write amplification break?** At hot-set concentration: WA ≈ depth per _batch_, so it breaks when updates-per-flush-window per hot key exceed ~5–10, i.e. sustained 10⁴ upd/s on ≤10³ hot keys on a 10⁷-key corpus.
**(c) Ref-per-retention-partition the right granularity?** Right for independent scopes (code ∞, logs 30 d, CAS 7 d) — genuinely clean. Wrong for downstream-reachability-dependent retention: a fact's interpretable lifetime is bounded by the shortest retention of anything it references, and ref expiry cannot express "expire the log but keep the build artifact it cites" without over-retaining or Expired mid-DAG — reachability is a monotone _union_ over roots and cannot express intersection semantics. Correct ~80% of the time; cross-partition provenance needs a first-class mechanism, not policy notes.

**(d) Expired contract vs. real consumers?** No for stock consumers — promisor misses are indistinguishable from corruption/network failure (§3.A4). Survives only behind `materialize(oid)`.

**(e) Missing for general-database status?** Secondary indexes under contention (livelock on low-entropy keys); cross-repo atomicity (nothing — needs saga/2PC over refs); row-level authorization (none); schema evolution (partially solved, §7). Verdict: **not a general database; a durable CAS-backed event store with snapshot reads.** Fine — but say it.

## 7. Amendment critique

- **A (codec tiering + embedded version).** Closes the encoding-migration identity gap correctly — codec epochs mean migration never rewrites identity — but only if each tier's encoding is canonical; the general codec's float representation (§4.1) falsifies that premise in-tree. Residual: reserved-name hacks (`_` marker entry) and the identity normal form's exclusion list are codec-version-locked forever.
- **B (migration-as-facts).** Real improvement over the shipped read-time-only upcast (every reader must carry every historical codec forever). But "migrated corpus is a rebuildable cache" collides with retention: rebuilding needs old-epoch facts, so the old partition cannot expire while any consumer reads old data — compaction scheduling silently becomes another instance of the GC crown-jewel problem. **Relocated, not closed.**
- **C (tombstones).** Necessary — the codec cannot distinguish absent from deleted in multi-writer contexts. But liveness = reachability **minus negation** requires a durable, ordered, replicated negation index: a small mutable database hidden under the immutability headline. Residual non-content mutable state: **ref order, tombstone ledger, pin registry, push authorization** — each needs a durability story; none has one. **Relocated.**

## 9. Verdict

- **Soundness: 6/10.** The invariants hold for content, but encoding determinism is currently violated by the shipped codec, and the metadata layer (refs, tombstones, pins) is an unowned mutable database inside the "immutable" design — the frontier recurses.
- **Novelty: 4/10.** Venti, Irmin, Dolt, and Iceberg jointly cover the architecture; the honest residual is the promisor-as-retention-dial composition and the agent-log economics — workshop-grade deltas.
- **Shipability: 4/10.** Cross-tier GC policy, the Expired-contract incompatibility with stock Git tooling, and the write-back durability window are each independently capable of sinking production use.

**Recommendation: research paper** — a focused one: _reachability-GC as a unified retention model across hot and cold CAS tiers_, with F1/F5/F6 as its evidence. Not a niche product yet; not dead. **Single gating risk:** the GC/retention policy spanning local and remote under cross-partition reachability edges — the proposer calls it the crown jewel; it is, and everything else is subordinate.

**Three strongest:** (1) ref-per-retention-partition doubles as concurrency sharding and retention scoping — the best idea, mostly unadvertised; (2) measured evidence over assertion — the pack-delta numbers are the right metric; (3) read-time upcast + frozen identity normal form cleanly solve identity stability under codec evolution.

**Three weakest:** (1) the metadata layer violates the immutability thesis it is supposed to exemplify; (2) the async write-back window contradicts "cold record as the record of truth"; (3) C2/C3 rest on single-batch packing and a wrong O(refs) claim — headline economics unproven at realistic cadence.
